# DentalPhotoOrganizer

Phase 8-B / version 0.9.1

DentalPhotoOrganizer は、口腔内写真を患者ごとに確認・整理し、確認完了後に患者ごとのフォルダへ安全に書き出す Windows デスクトップアプリです。

元画像ファイルは変更しません。取り込み時は画像メタデータを Supabase に登録し、写真確認・撮影方法チェック・書き出し前確認を通して、患者写真の混入や分類ミスを減らすことを目的とします。

## 画面構成

### Dashboard

Dashboard は、取り込んだ写真数や確認待ち件数などを表示します。

Supabase の環境変数が未設定の場合も、アプリはクラッシュせず未設定状態として表示します。

### Import

Import 画面では、Electron の main process 経由でローカルフォルダを選択します。

React 側から直接ファイルシステムを操作しません。

対象拡張子:

- `.jpg`
- `.jpeg`
- `.png`

拡張子の大文字小文字は区別しません。

取込時に登録する主な情報:

- `original_filename`
- `original_path`
- `file_hash`
- `file_size`
- `mime_type`
- `imported_at`
- `review_status`
- `export_status`

元画像ファイルに対して以下は行いません。

- 移動しない
- リネームしない
- 削除しない
- 画像加工しない

同じ `file_hash` がすでに `photos` に存在する場合は、重複登録せず、取込結果で重複スキップとして扱います。

### 写真確認

写真確認画面では、患者ごとにまとまった写真を人間が確認します。

主な機能:

- 確認待ち / 確認済みの切り替え
- 患者ID、撮影日、担当医、撮影者、撮影方法の編集
- 写真ごとの撮影種別ラベル付け
- 5枚法 / 9枚法などの撮影基準チェック
- 未分類写真や基本分類以外の写真の注意表示
- 選択中の写真を別の患者へ移動
- 選択中の写真を新しい患者として分離
- 同じ患者の写真としてまとめる
- 一時保存
- 確認完了

UIでは、内部概念の「患者写真セット」をそのまま多用せず、「患者」「この患者の写真」「患者ごとの写真」などの表現を優先します。

### 書き出し

書き出し画面では、確認完了した写真を患者ごとのフォルダへコピーします。

元の写真は変更されません。

主な機能:

- 書き出し対象の患者一覧
- 書き出し前の最終確認
- 患者ID、撮影日、撮影方法、写真枚数、担当医、撮影者の表示
- 撮影基準チェックの表示
- この患者の写真サムネイル表示
- 写真確認画面へ戻る導線
- 書き出し先フォルダ選択
- 書き出し開始

内部状態の `approved`、`ready_for_export`、`exported` は、UIでは「確認完了」「書き出し待ち」「書き出し済み」として表示します。

書き出し成功時には、実際にコピーされた患者ごとのフォルダパスを `photo_groups.official_export_folder_path` に記録し、`official_exported_at` に記録時刻を保存します。

アプリが管理する正式な書き出し先は、施設・医局で設定した既定フォルダに集約します。個人PC、SDカード、USBメモリなどへの二次コピーは、アプリの追跡対象外です。

追加書き出しも、任意の個人フォルダではなく正式な書き出し先に対して行う方針です。既存ファイルは黙って削除・上書きしません。

### Search

Search 画面では、Supabase の `photo_groups` / `photo_group_items` をもとに、患者ごとの写真を検索できます。

検索条件:

- 患者ID
- 撮影日 From / To
- 担当医
- 撮影者

検索結果には、患者ID、撮影日、撮影方法、写真枚数、担当医、撮影者、写真確認状態、書き出し状態を表示します。

患者ごとの写真を判別しやすくするため、検索結果カードには最大5枚のサムネイルを表示します。

Search結果では、正式書き出し先が記録済みかどうかを「記録あり / 未記録」で確認できます。長い保存先パスを常時表示して画面を崩さないため、現時点では記録有無のみを通常表示します。

`pending` / `approved` / `ready_for_export` / `exported` などの内部値は、UIでは「確認待ち」「確認完了」「書き出し待ち」「書き出し済み」として表示します。

検索結果の「写真確認で開く」から、該当患者の写真確認画面へ移動できます。

書き出し済みの患者も検索結果に表示します。書き出し済みは完全ロックではなく、将来的な再確認や追加書き出しの対象になり得ます。

この検索はDBメタデータの読み取りのみを行い、元画像ファイルは変更しません。

### Settings

Settings 画面では、取込元、保存先、確認必須設定、アプリ情報などを表示します。

## 写真確認ワークフロー

1. 写真を取り込む。
2. QRコード、ファイル順、時刻などをもとに、患者ごとの候補として仮分類する。
3. 人間がこの患者の写真を確認する。
4. 患者ID、撮影日、担当医、撮影者、撮影方法を確認・修正する。
5. 写真ごとの撮影種別を確認・修正する。
6. 混入写真があれば、別の患者へ移動、または新しい患者として分離する。
7. 入力途中の場合は一時保存する。
8. 写真と患者情報を確認できたら確認完了にする。

自動分類やQR情報は仮説であり、最終判断ではありません。書き出し前には必ず人間による写真確認を行います。

## 書き出しワークフロー

1. 確認完了した患者を選ぶ。
2. 書き出し前の最終確認で、患者ID、撮影日、撮影方法、写真枚数、サムネイルを確認する。
3. 問題があれば写真確認画面へ戻って修正する。
4. 書き出し先フォルダを選択する。
5. 書き出し開始を実行する。
6. 患者ごとのフォルダへ写真をコピーする。

書き出しはコピー出力です。元画像ファイルは変更しません。

書き出し済みは完全ロックではありません。後から写真の追加、分類修正、再確認、追加書き出しが必要になる可能性があります。既存の書き出し済みフォルダを破壊的に削除・上書きしない方針を優先します。

## DB / Supabase

主なテーブル:

- `photos`: 元画像ファイル単位のメタデータ
- `photo_groups`: 患者ごとの写真のまとまりを表す内部テーブル
- `photo_group_items`: `photos` と `photo_groups` の中間テーブル
- `review_logs`: 写真確認・確認完了・修正履歴の監査ログ用テーブル
- `staff`: 担当医・撮影者などのスタッフマスタ

注意:

- `supabase/schema.sql` は初期MVP時代のスキーマ定義を含みます。
- 現行DBと完全には一致しない可能性があります。
- DB変更を行う場合は、原則として `supabase/phase*.sql` を追加してください。
- `supabase/schema.sql` を現行DBの完全な source of truth として扱わないでください。
- 本番運用前には RLS、認証、権限設計を必ず行ってください。

## Electron API 変更時の注意

Electron preload 経由の API を追加・変更する場合は、`electron/preload.ts` だけでなく `scripts/write-preload.cjs` も確認してください。

Renderer から直接 Node.js / `fs` API を呼び出さないでください。

## 設計方針

- 元画像ファイルは不変
- 患者情報はDBで管理
- 作業中ファイル名へ患者IDを埋め込まない
- 自動分類は仮分類のみ
- 人間による写真確認を必須にする
- 確認完了後のみ書き出し対象にする
- 書き出し前にも最終確認できるようにする
- 書き出しはコピー出力とし、元画像を変更しない
- 書き出し済みを完全ロックとして扱わない
- 操作疲れ、判断疲れを減らす
- UI文言は非開発者が理解しやすい表現を優先する

## 環境変数

`.env` を作成し、Supabase の Project URL と anon key を設定します。

```env
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=
```

`.env` は Git 管理対象外です。共有用の雛形は `.env.example` を使用してください。
