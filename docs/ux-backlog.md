# UX Backlog

## 目的

このドキュメントは、DentalPhotoOrganizer の実運用で見つかったユーザビリティ上の違和感や改善案を蓄積するためのバックログである。

現時点では設計メモとして扱い、必ずしも実装を前提としない。

ある程度アイデアが蓄積した段階で優先順位を整理し、Phaseとして実装する。

---

# 運用ルール

- 実際にソフトを使用して感じたことを記録する
- アイデアレベルでも記録する
- 実装方法ではなく「困ったこと」「改善したいこと」を書く
- 同じ内容が複数回出てきた場合は重要度を見直す
- 実装完了後は Done へ移動する
- 実装時は必要に応じて GitHub Issue や Phase 計画へ昇格させる

---

## Import画面から開発者向け文言を排除する

### 画面

Import

### 現象

Import画面に「Electron API」「preload」「SHA-256 file_hash」「photos テーブル」など、一般ユーザーには理解不要な技術用語が表示されている。

ユーザーが知りたいのは、内部実装ではなく「写真を取り込める準備ができているか」「どの処理が行われるか」である。

### 理想

技術用語をユーザー向け表現へ置き換える。

例:

- 「Electron API接続済み」→「フォルダ選択の準備ができました」
- 「Electron経由でフォルダ選択」→「フォルダを選択」
- 「jpg / jpeg / png を抽出」→「対象画像を読み込み」
- 「SHA-256 file_hash を計算」→「重複画像を確認」
- 「QRコード検出結果をメタデータとして保存」→「QRコードを解析」
- 「photos テーブルへメタデータ登録」→「患者情報として登録」

開発者向けの詳細情報は通常表示しない。必要な場合は開発モードやログで確認できるようにする。

### 優先度

High

### 備考

この画面は実運用で最初に触る画面であり、開発者向け文言が残るとソフト全体の印象に影響する。

Issue #2 / Phase9-A で対応済み。

## Review画面でQR画像の占有率が高すぎる

### 画面

患者情報・写真確認

### 現象

QRコード画像が画面中央の大部分を占めており、重要な口腔内写真よりも視線を奪っている。

Review画面の主目的は、患者情報・撮影方法・不足写真・口腔内写真のまとまりを確認することであり、QR画像は補助情報である。

加えて、表示中の写真から前後の写真へ移動する導線が弱い。写真確認中は、画像一覧や下部操作に視線を移さず、表示中の画像上で前後の写真へ切り替えられる方が自然である。

### 理想

QR画像は確認用の補助情報として扱い、サイズを小さくするか、初期状態では折りたたむ。

口腔内写真が主役となるレイアウトへ変更する。

例:

- QR画像を小さなサムネイル表示にする
- 「QR画像を表示」ボタンで展開する
- 口腔内写真一覧を優先して表示する

写真確認の操作性として、表示中の画像から直感的に前後移動できるようにする。

例:

- 画像左側に「前の写真」ボタンを表示する
- 画像右側に「次の写真」ボタンを表示する
- 画像上で左右フリック、またはスワイプして前後の写真へ切り替える
- 現在位置を `1 / 5` のように表示する
- 可能であればキーボードの左右矢印でも切り替えられるようにする

### 優先度

High

### 備考

情報設計として、QR画像は「元データ確認」のための補助レイヤーに置くのが自然である。

前後移動導線の追加は、Issue #4 / Phase9-C の追加要件として扱う。

## 撮影方法と撮影種別プルダウンが連動していない

### 画面

患者情報・写真確認

### 現象

患者の撮影方法を「5枚法」に設定しても、画像ごとの撮影種別プルダウンには14枚法の撮影部位が表示される。

例として、5枚法にもかかわらず「右側方面観」「左側方面観」「上顎右側臼歯部」「下顎左側臼歯部」などが選択肢として表示される。

### 理想

撮影方法に応じて、選択可能な撮影種別を切り替える。

5枚法・9枚法・14枚法の正式な撮影種別マスターは `docs/shooting-method.md` を参照する。

### 優先度

High

### 備考

UXだけでなく仕様整合性の問題である。

撮影基準チェック、プルダウン候補、自動判定は同じ撮影方法マスターデータを参照する設計が望ましい。

Issue #3 / Phase9-B で対応済み。

## Search画面の余白が多く、検索結果の表示領域が狭い

### 画面

Search

### 現象

検索条件エリアが画面の大部分を占有しており、検索結果一覧の表示領域が狭い。

実際の利用では、検索条件を入力する時間よりも検索結果を見て患者を探す時間の方が長い。そのため、画面配分が利用頻度と一致していない。

### 理想

検索条件はコンパクトにまとめ、検索結果をより広く表示する。

例:

- 検索条件の高さを縮小する
- 検索ボタンとクリアボタンを通常サイズにする
- 検索結果エリアを広くする
- 必要に応じて検索条件を折りたたみ可能にする

### 優先度

High

### 備考

Search画面は検索条件入力画面ではなく、実運用上は「写真ライブラリ」に近い役割を持つ。検索結果の視認性を優先する。

## 患者間ドラッグ&ドロップで写真を移動できるようにする

### 画面

患者情報・写真確認

### 現象

他の患者の写真が混ざっていた場合、現在は右側パネルで移動先患者を選択し、「この写真を移動」を押す必要がある。

写真を見ながら患者一覧を確認している場面では、写真をそのまま患者カードへドラッグして移動できる方が直感的である。

### 理想

表示中の写真またはサムネイルをドラッグし、左側の患者カードへドロップすることで、写真を別患者へ移動できるようにする。

理想の流れ:

1. 混ざっている写真をドラッグする
2. 左側の移動先患者カードへドロップする
3. 「患者Xへ移動しますか？」と確認する
4. 確認後、写真が移動する
5. 「写真を患者Xへ移動しました」と表示する
6. 可能であれば「元に戻す」を表示する

UX要件:

- ドラッグ開始時に、ドロップ可能な患者カードが分かる
- ドロップ先の患者カードがハイライトされる
- 誤操作防止のため、移動前に確認を挟む
- 移動完了後にトーストなどで結果を表示する
- 将来的に複数枚選択→まとめて移動できる設計を妨げない

### 優先度

High

### 備考

この改善はIssue #4の画像ビューア改善とは別であり、写真閲覧ではなく患者間の写真整理操作を効率化する新機能である。

Issue #6 / Phase10 として管理する。

# Low

## 口腔内写真と補助画像の命名整理

### 画面

全体 / 患者情報・写真確認 / Import

### 現象

Issue #4 の途中実装では、QRを除いた写真を `intraoralPhotos`、QR画像を `qrPhotos` として分離している。

現時点では分かりやすいが、将来的にQR以外にもバーコード、患者ラベル、OCR対象画像などの補助画像が増える可能性がある。

その場合、`qrPhotos` だけを特別扱いするより、臨床写真と補助画像を概念として分ける方が拡張しやすい。

### 理想

将来的なリファクタリングで、以下のような命名・概念整理を検討する。

- `clinicalPhotos`: 口腔内写真など、確認・分類・書き出しの主対象となる臨床写真
- `auxiliaryPhotos`: QR、バーコード、患者ラベル、OCR対象画像など、患者情報取得や確認補助のための画像

この整理により、QRだけでなくバーコード対応やOCR対応を追加しても、画像の役割分担が崩れにくくなる。

### 優先度

Low

### 備考

Phase10以降のリファクタリング候補として保持する。

今すぐ実装する必要はないが、バーコード対応や補助画像の種類が増えた段階で検討する価値がある。
